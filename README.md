# AIMS-UI

AIMS-UI is the browser and edge layer for the AIMS Communications Hub. It ships the operator console, the embeddable CogniPal widget and a Cloudflare Worker gateway. AIMS remains the authoritative backend for communication routing, conversation state, automation, approvals and audit history; AIMS-UI presents those capabilities and keeps privileged credentials out of browser code.

## Architecture and shipped surfaces

| Area | Source | Production output | Responsibility |
|---|---|---|---|
| Operator console | `apps/console` | `dist/site/console` | Unified inbox, DMs/comments, approvals, contacts, workflows, quarantine, analytics, settings and conversation workspace |
| Shared browser modules | `packages/*` | JavaScript folded into `dist/site/console/app.js`; design tokens copied to `dist/site/console/lib` | API client, contracts, formatting and design tokens |
| CogniPal widget | `apps/widget` | `dist/site/widget` | Shadow-DOM website chat client with separately cached module/CSS assets using the public gateway contract |
| Gateway Worker | `workers/gateway` | `dist/gateway` | HIVE session boundary, delegated AIMS proxy, widget persistence/relay, health routes and security headers |
| Build metadata | generated by `scripts/build.mjs` | `dist/build-manifest.json`, `dist/gateway/build-meta.js` | Release SHA, branch and deployment-source digest used by exact-artifact verification |

The Worker is deployed on Cloudflare with static assets bound as `ASSETS`. The shipped public widget also requires the `DB` D1 binding. D1 stores widget sessions/messages and the durable delivery outbox; it is not the system of record for the AIMS operator conversation model.

## Console capabilities

- Unified Inbox with nested **DMs** and **Comments** queues.
- Facebook and Instagram DMs grouped together; Facebook, Instagram and YouTube comments grouped separately.
- Filters for status, channel, priority, owner, tag, overdue and AI state.
- Conversation thread, contact context, AI context, notes, assignment, reply and takeover controls.
- Approval, quarantine, workflow, analytics, notification and settings surfaces.
- Social capability/status display, webhook reconciliation and controlled polling.
- Live API mode only. Connection failures remain visible and never fall back to invented data.

## Secure HIVE hand-off

HIVE opens the console through `/api/auth/comms-handoff`. HIVE-UI creates a short-lived signed hand-off token and redirects to `https://chat.jonathan-harris.online/console/#handoff=...`. The fragment is consumed immediately and removed from the address bar.

The browser then uses same-origin `/console/api`. The gateway exchanges the short-lived HIVE hand-off for an HttpOnly console cookie and delegates to AIMS server-side. If `HIVE_COMMS_HANDOFF_SECRET` is configured, the gateway verifies the hand-off locally; otherwise it uses the configured HIVE identity verifier. `COMMS_HUB_RBAC_DELEGATION_SECRET`, AIMS credentials and provider secrets never enter the browser bundle.

## Gateway boundaries

- `/console/api/*` — authenticated proxy to protected AIMS Comms Hub routes.
- `/widget/*` — public widget session/message contract backed by D1 and signed AIMS relay.
- `POST /comms-hub/intake/chat` and `/comms-hub/intake/chat/sync` — signed first-party pass-through to AIMS.

The widget treats AIMS as the authoritative conversation transcript. Its authenticated polling route signs a server-to-server `/comms-hub/intake/chat/sync` request and merges returned AIMS messages with the gateway delivery ledger.

## Health model

Health endpoints have deliberately different scopes:

- `GET /livez` is liveness only. It returns `200` when the Worker can execute and does not depend on production bindings or upstream AIMS health.
- `GET /readyz` is fail-closed readiness. It verifies required configuration/bindings, confirms the D1 `DB` binding is present and checks the configured AIMS Comms Hub health endpoint. It deliberately **does not query D1 tables or schema**.
- `GET /health` is a backwards-compatible alias of `/readyz`.
- D1 schema/table validation belongs to migration/diagnostic commands and functional widget operations, where a failed query is actionable.
- `npm run test:deployed` is broader than liveness/readiness: it validates the deployed release metadata, production bindings, D1-backed widget flow, console asset/security policy and, when credentials are supplied, the HIVE hand-off and delegated AIMS proxy.

## Local development and validation

The repository intentionally has no npm application dependencies. Use the pinned Node/npm versions from `package.json`; CI verifies them exactly.

```bash
npm run dev
```

The local console preview is available at `http://127.0.0.1:4173/apps/console/`.

Run the complete repository-native validation before publishing changes:

```bash
npm run validate
```

That command runs linting, source/configuration checks, all Node tests, committed-secret scanning, the dependency gate, a clean build and the bundle-budget gate. `npm run build:production` additionally requires exact release metadata; `npm run verify:deploy-artifact` proves the generated artifact still matches the release checkout.

## Build and JavaScript bundle budget

`npm run build` recreates `dist` from source on every run. The console's internal JavaScript modules are folded into one production browser module to avoid duplicate compression/request overhead while preserving the modular source tree. Deployable JavaScript is compacted by `scripts/compact-javascript.mjs`, which preserves the lexical token stream and re-parses generated modules. CSS is compacted separately by `scripts/compact-css.mjs`, and the CogniPal Shadow-DOM stylesheet ships as its own cacheable asset instead of inflating JavaScript. No network-fetched build dependency is required.

Bundle policy lives in `config/bundle-budget.json` and is enforced by `npm run check:bundle-budget`:

- gzipped JavaScript warning threshold: **42,750 bytes** (95% of the hard ceiling);
- gzipped JavaScript hard ceiling: **45,000 bytes**;
- total bundle, CSS and largest-asset hard limits remain separately enforced.

The checker always reports actual gzipped JavaScript, warning limit, hard limit, remaining bytes, percentage consumed and state. Entering the warning band is visible in CI but does not fail the build. Exceeding the hard ceiling still fails validation and release.

When JavaScript grows unexpectedly, inspect the per-file production output under `dist`, then look for dead imports/code, duplicate helpers, repeated vendor/polyfill inclusion, embedded data and features that can be split or deferred without changing behaviour. Raising the hard ceiling is **not** the default fix. A budget increase must be an explicit reviewed configuration change supported by bundle analysis and a technical reason that optimisation is unsafe or disproportionate.

## Configuration and Cloudflare bindings

Non-secret production values are defined in `wrangler.toml`; secrets are configured in Cloudflare and never committed. The effective production contract includes:

| Name | Type | Purpose |
|---|---|---|
| `AIMS_API_BASE_URL` | variable | AIMS backend origin |
| `CONSOLE_ALLOWED_ORIGINS` | variable | exact browser origins allowed to use console routes |
| `WIDGET_ALLOWED_ORIGINS` | variable | exact website origins allowed to create widget sessions |
| `WIDGET_ALLOWED_SITE_IDS` | variable | site IDs accepted by the public widget |
| `HIVE_IDENTITY_VERIFY_URL` / method | variable | HIVE identity fallback when no shared hand-off secret is configured |
| `DB` | D1 binding | widget session/message ledger and delivery outbox |
| `ASSETS` | assets binding | built console/widget/static files |
| `AIMS_API_KEY` | secret | server-side AIMS authentication |
| `COMMS_HUB_RBAC_DELEGATION_SECRET` | secret | signs delegated AIMS operator identity |
| `CHAT_SESSION_SECRET` | secret | signs public widget session tokens |
| `COGNIPAL_WEBHOOK_SECRET` | secret | signs widget relay/synchronisation traffic to AIMS |
| `HIVE_COMMS_HANDOFF_SECRET` | optional secret | local verification of HIVE hand-off tokens |
| `COGNIPAL_API_KEY` | optional secret | provider-compatible `/sessions/*` routes only |

Use `.env.example` only as a safe local shape reference; never place production credentials in source files or browser configuration.

## Production deployment

There is one supported production release path:

```bash
npm run deploy:production
```

The governed command runs validation, performs a clean production build, requires an exact full Git SHA and release branch, verifies the generated source digest/release metadata and then invokes the pinned Wrangler release command. CI may provide `AIMS_UI_RELEASE_SHA` and `AIMS_UI_RELEASE_BRANCH`, but values that contradict the checked-out Git commit or branch are rejected.

`scripts/wrangler-build.mjs` also protects ordinary Wrangler invocation by rebuilding/validating the production artifact. This is defence in depth, not a second documented release procedure. After deployment, run the deployed-integration workflow against the exact published SHA.

The root Wrangler configuration registers a five-minute scheduled trigger for the D1-backed widget delivery outbox. Apply `workers/gateway/schema.sql` before deployment and retain that trigger so persisted visitor messages are retried while AIMS is temporarily unavailable.

## Security and release gates

- `npm run secret:scan` rejects committed literal credentials.
- `npm run audit:dependencies` requires a lockfile and npm audit if dependencies are ever added.
- `npm run check:bundle-budget` enforces warning/hard bundle policy.
- `npm run verify:deploy-artifact` verifies exact release metadata and deployment-source digest.
- CI retains an exact-SHA release attestation only after validation, production build, artifact verification and bundle checks pass.
- Production source checks reject demo/mock markers and documentation/workflow deployment paths that bypass the governed release command.

## Widget

The widget is isolated in Shadow DOM, persists its session, supports polling/retry/cold-start states and includes keyboard/accessibility controls. Website installation is governed in the website repository; the current public website uses its own first-party CogniPal assets and Pages Functions rather than depending on this repository alone for installation.

See `workers/gateway/README.md`, `apps/widget/README.md`, `docs/architecture.md` and `SECURITY.md` for component-level detail.
